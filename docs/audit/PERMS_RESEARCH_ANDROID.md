# PERMS_RESEARCH_ANDROID — Permisos, FGS, alarmas y restricciones (API 26–36)

App: `com.dmujeres.traccar` (tracking GPS en background con FGS tipo `location`), targetSdk 35, minSdk 26, distribuida por sideload/OTA (sin Play Store).
Investigación: 2026-09-19. Fuentes oficiales (developer.android.com, AOSP/issuetracker) + foros (StackOverflow, Android Police, GitHub), etiquetados como secundarios donde aplica.

## 0. Resumen ejecutivo

- La vía correcta sigue siendo: `ACCESS_BACKGROUND_LOCATION` + FGS `location` + `ACCESS_FINE_LOCATION`; en Android 11+ el "todo el tiempo" se concede SOLO desde Ajustes (nunca en diálogo).
- Android 14+ obliga a `FOREGROUND_SERVICE_LOCATION` y a tener ubicación ON + permiso antes de `startForeground()`: si falta → `SecurityException` (incluso desde `BOOT_COMPLETED` con GPS apagado).
- `BOOT_COMPLETED` como arranque de FGS está permitido y `location` quedó EXENTO de las restricciones de Android 15/16.
- Alarmas exactas: desde Android 14 `SCHEDULE_EXACT_ALARM` viene denegada por defecto en instalaciones nuevas; `USE_EXACT_ALARM` es solo reloj/calendario. Para tracking lo correcto es `setAndAllowWhileIdle()`/inexactas; además, estar exento de optimización de batería permite alarmas exactas sin el permiso especial.
- Android 16 (target 36): los jobs que corren junto a una FGS ahora tienen cuota; no usar WorkManager para subidas continuas del tracker.
- No existe API pública para autostart OEM, conceder permisos runtime, activar Accessibility ni tocar AppOps.

## 1. Permisos runtime por versión

### Android 10 (API 29)
- `ACCESS_BACKGROUND_LOCATION` se introduce como permiso separado; solo afecta el acceso con la app en background. Apps con target ≤28 lo reciben automáticamente al instalar; con target 29+ hay que declararlo y pedirlo. Fuente: https://developer.android.com/about/versions/10/privacy/changes (sección "Location access / ACCESS_BACKGROUND_LOCATION").
- Un FGS que use ubicación debe declarar `android:foregroundServiceType="location"` (obligatorio para target 29+). Fuente: https://developer.android.com/develop/sensors-and-location/location/permissions (sección "Foreground location").
- En Android 10 el diálogo SÍ incluye "Permitir todo el tiempo" cuando se pide background; en 11+ ya no. Fuente: https://developer.android.com/develop/sensors-and-location/location/permissions/background ("Permission dialog contents depend on target SDK version").
- No pedir foreground y background en la misma llamada: el sistema ignora la solicitud de background y el flujo correcto es incremental (fine/coarse → luego background). Fuente: https://developer.android.com/develop/sensors-and-location/location/permissions/runtime ("If you request a foreground location permission and the background location permission at the same time, the system ignores the request and doesn't grant your app either permission").

### Android 11+ (API 30–36)
- El diálogo ya NO ofrece "Allow all the time"; la usuaria debe habilitar "Permitir todo el tiempo" en Ajustes > Ubicación > [app]. Fuente: https://developer.android.com/develop/sensors-and-location/location/permissions/background.
- Flujo recomendado: si `shouldShowRequestPermissionRationale()` == true, mostrar UI educativa (motivo + etiqueta localizada vía `getBackgroundPermissionOptionLabel()`) y opción de declinar. Fuente: misma página.
- Pedir foreground+background juntos en target 11+ hace que el sistema ignore y no conceda NINGUNO. Fuente: https://developer.android.com/about/versions/11/privacy/location ("Request background location separately").
- Denegar dos veces = "no volver a preguntar"; no reintentar el diálogo, guiar a Ajustes. Fuente: https://developer.android.com/about/versions/11/privacy/permissions ("Permission dialog visibility").
- Permiso "Solo esta vez" aplica a ubicación foreground/micrófono/cámara. Fuente: https://developer.android.com/about/versions/11/privacy/permissions ("One-time permissions").
- Si la usuaria elige ubicación aproximada (coarse), esa precisión también aplica al background. Fuente: https://developer.android.com/develop/sensors-and-location/location/permissions/background ("User can affect background location accuracy").

### Android 13 (API 33): POST_NOTIFICATIONS
- Permiso runtime `POST_NOTIFICATIONS` (dangerous); declarar en manifest y pedir en contexto, tras explicar. Fuente: https://developer.android.com/develop/ui/views/notifications/notification-permission.
- NO se necesita `POST_NOTIFICATIONS` para iniciar un FGS; sí la notificación del servicio. Si la usuaria deniega, la notificación del FGS no aparece en el drawer pero sí en el Task Manager, y el FGS sigue funcionando. Fuentes: https://developer.android.com/develop/ui/views/notifications/notification-permission ; https://developer.android.com/about/versions/13/behavior-changes-13 ("Notification permission affects foreground service appearance").
- Al actualizar el dispositivo a 13, el sistema pre-concede el permiso a apps existentes. Fuente: notification-permission ("Effects on updates to existing apps").
- Android 13+ permite a la usuaria detener el FGS desde el Task Manager; manejar `onDestroy`/reinicio. Fuente: https://developer.android.com/about/versions/13/behavior-changes-all ("Task Manager").

### Android 14 (API 34): FGS type location + while-in-use
- Todo FGS debe declarar tipo; `location` exige `FOREGROUND_SERVICE_LOCATION` en manifest (además de `FOREGROUND_SERVICE`). Sin tipo → `MissingForegroundServiceTypeException`; sin permiso de tipo → `SecurityException` en `startForeground()`. Fuente: https://developer.android.com/about/versions/14/changes/fgs-types-required.
- Prerrequisitos runtime de `location`: servicios de ubicación ON y `ACCESS_COARSE_LOCATION` o `ACCESS_FINE_LOCATION` concedido. Fuente: https://developer.android.com/develop/background-work/services/fgs/service-types (tipo Location).
- Restricción while-in-use: no se puede crear un FGS `location` desde background aunque se cumpla una exención de arranque, salvo que se tenga `ACCESS_BACKGROUND_LOCATION`. Con ese permiso y tipo `location`, el acceso a ubicación funciona siempre. Fuente: https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start ("Restrictions on starting foreground services that need while-in-use permissions").
- Caso borde documentado en issuetracker: si se arranca el FGS `location` desde `BOOT_COMPLETED` con ubicación del sistema APAGADA, lanza `SecurityException` aunque los permisos estén concedidos (el check exige location ON). Hay que manejar la excepción y reintentar al habilitarse. Fuente: https://issuetracker.google.com/issues/294408576.

### Android 15 (API 35)
- `BOOT_COMPLETED` no puede lanzar FGS de ciertos tipos; `location` está EXENTO (igual que `connectedDevice`, `remoteMessaging`, `health`, `systemExempted`, `specialUse`). Fuentes: https://developer.android.com/about/versions/15/behavior-changes-15 ("Restrictions on BOOT_COMPLETED broadcast receivers launching foreground services") ; https://developer.android.com/about/versions/15/reference/compat-framework-changes (`FGS_BOOT_COMPLETED_RESTRICTIONS`).
- Timeout de 6 h/24 h SOLO para `dataSync` y `mediaProcessing` (no aplica a `location`). No usar `dataSync` para subidas del tracker. Fuente: https://developer.android.com/develop/background-work/services/fgs/timeout.
- `SYSTEM_ALERT_WINDOW`: para lanzar FGS desde background se exige overlay visible (exención más estricta). Fuente: https://developer.android.com/develop/background-work/services/fgs/changes (Android 15).
- "Stopped state" (force-stop): se cancelan todos los `PendingIntent` de la app; alarmas previas no disparan hasta que la usuaria abra la app. Fuente: https://developer.android.com/about/versions/15/behavior-changes-all ("Changes to package stopped state").
- Sin cambios a la exención de batería, Doze ni a `SCHEDULE_EXACT_ALARM`.

### Android 16 (API 36)
- Jobs en background iniciados desde una FGS ahora cumplen cuota de ejecución (aplica a TODAS las apps en dispositivo 16, independiente del target). WorkManager/JobScheduler/DownlandManager quedan sujetos. Para transferencias usar "user-initiated data transfer jobs". Fuentes: https://developer.android.com/develop/background-work/services/fgs/changes (Android 16) ; https://developer.android.com/about/versions/16/behavior-changes-all#job-quota-opt.
- `JobInfo.Builder#setImportantWhileForeground()` se ignora desde 16 (`isImportantWhileForeground()` devuelve false). Fuente: behavior-changes-all 16 (misma sección).
- BAL (restricción de inicio de actividades): NO cambia a favor; siguen vigentes las excepciones (ventana visible, PendingIntent del sistema/notificación con tap, `SYSTEM_ALERT_WINDOW`, `START_ACTIVITIES_FROM_BACKGROUND`, IME, etc.). Abrir Ajustes/OEM desde un servicio en background sigue bloqueado salvo excepción. Fuente: https://developer.android.com/guide/components/activities/secure-bal ("When background activity starts are allowed").
- API 36 agrega `ActivityOptions.MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE` y `ALLOW_ALWAYS` para que el emisor de un `PendingIntent` haga opt-in explícito. Fuente: https://developer.android.com/reference/android/app/ActivityOptions.
- "Safer Intents" (intent redirection) endurece intents con sub-intents; no afecta intents explícitos hacia `Settings`. Fuente: https://developer.android.com/about/versions/16/behavior-changes-all ("Improved security against Intent redirection attacks").
- Alarmas exactas: sin cambios nuevos en 16; rige el default-deny de Android 14 (ver §3). Fuentes: https://developer.android.com/about/versions/14/behavior-changes-all ; páginas de behavior changes 15/16 (sin sección de alarmas).

### ¿Existen APIs para leer el estado? (confirmado)
- `PowerManager.isIgnoringBatteryOptimizations(String pkg)` — API 23+, sin permiso; indica si la app está en la allowlist. Fuente: https://developer.android.com/reference/android/os/PowerManager#isIgnoringBatteryOptimizations(java.lang.String) y https://developer.android.com/training/monitoring-device-state/doze-standby.
- `ActivityManager.isBackgroundRestricted()` — API 28+, sin permiso; true si la usuaria restringió batería/background de la app. Fuente: https://developer.android.com/reference/android/app/ActivityManager#isBackgroundRestricted().
- `UsageStatsManager.getAppStandbyBucket()` — API 28+. La referencia dice "Requires PACKAGE_USAGE_STATS", pero AOSP documenta que los métodos que solo devuelven info de la app que llama NO requieren ese permiso (`getAppStandbyBucket()`, `queryEventsForSelf`). `getAppStandbyBucket(String pkg)` es `@SystemApi` (no disponible para apps normales). `PACKAGE_USAGE_STATS` es acceso especial (Ajustes > Acceso especial > Uso), no diálogo runtime. Fuentes: https://developer.android.com/reference/kotlin/android/app/usage/UsageStatsManager ; https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/app/usage/UsageStatsManager.java ; https://developer.android.com/topic/performance/appstandby.
- Bucket `restricted`: no puede lanzar FGS, los FGS existentes salen de foreground, alarmas no disparan, jobs no se ejecutan; con target 13+ tampoco se entrega `BOOT_COMPLETED`. Fuentes: https://developer.android.com/about/versions/13/behavior-changes-all#battery-resource-utilization ; https://developer.android.com/about/versions/13/behavior-changes-13.

## 2. Batería / Doze

- `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (API 23+) siguen funcionando en Android 12–16: permiso normal y diálogo de sistema para allowlist. Fuente: https://developer.android.com/training/monitoring-device-state/doze-standby ("Support for other use cases") ; https://developer.android.com/reference/android/provider/Settings#ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS.
- La restricción es de POLÍTICA PLAY, no técnica: "Google Play policies prohibit apps from requesting direct exemption ... unless the core function of the app is adversely affected" (la app no está en Play, pero la política aplica a auto-update fuera de Play si algún día se publica). Fuentes: doze-standby (nota) ; https://support.google.com/googleplay/android-developer/answer/16559646 ("Device and Network Abuse": self-updates fuera de Play y bypass de power management) ; https://developer.android.com/docs/quality-guidelines/archive/core/core-app-quality-2021-02-10 (FN-B2/PS-B1).
- Alternativa sin permiso: `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` (abre la lista general; la usuaria busca la app). Fuente: https://developer.android.com/reference/android/provider/Settings#ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS.
- Doze (reposo profundo, estacionario, sin carga, pantalla apagada): suspende red, ignora wake locks, difiere jobs/syncs y alarmas estándar, no escanea Wi-Fi; `setAndAllowWhileIdle()`/`setExactAndAllowWhileIdle()` y `setAlarmClock()` sí disparan (estas últimas sacan del Doze). Fuente: https://developer.android.com/training/monitoring-device-state/doze-standby ("Doze restrictions") ; https://developer.android.com/topic/performance/power/power-details.
- Exención parcial de batería: la app "puede usar la red y mantener partial wake locks durante Doze y App Standby"; otras restricciones siguen aplicando. Fuente: doze-standby ("Doze checklist / Acceptable use cases for exemption").
- Android 7+: Doze ligero al apagar pantalla (aunque haya movimiento) y Doze completo solo estacionario; el completo restringe GPS y escaneos Wi-Fi. Fuente: https://developer.android.com/about/versions/nougat/android-7.0-changes#doze.
- Límite de ubicación en background (Android 8+, API 26): app en background recibe ubicación "solo unas pocas veces por hora"; el FGS es el mecanismo para updates continuos. Fuentes: https://developer.android.com/develop/sensors-and-location/location/background ; https://developer.android.com/about/versions/oreo/background-location-limits.
- Android 11+: FGS iniciada en background sin `ACCESS_BACKGROUND_LOCATION` no puede acceder a ubicación. Fuente: https://developer.android.com/about/versions/oreo/background-location-limits (nota).

## 3. Alarmas exactas

- API 31+: `SCHEDULE_EXACT_ALARM` (special app access, "Alarmas y recordatorios") es requerido para `setExact()`, `setExactAndAllowWhileIdle()` y `setAlarmClock()`; si no, `SecurityException`. Se solicita con `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`. Fuente: https://developer.android.com/develop/background-work/services/alarms ("Set an exact alarm") ; https://developer.android.com/reference/android/app/AlarmManager#canScheduleExactAlarms().
- API 31–33: se concede al instalar (revocable). Android 14+ (API 34): denegada por defecto en instalaciones NUEVAS que apunten a 33+; upgrades conservan la concesión y backup/restore la dejan denegada. Fuente: https://developer.android.com/about/versions/14/changes/schedule-exact-alarms ("Affected apps").
- `USE_EXACT_ALARM` (API 33+): permiso normal, concedido al instalar, SOLO para apps de reloj/calendario (restringido por política Play). No aplica a un tracker. Fuentes: https://developer.android.com/develop/background-work/services/alarms ; https://developer.android.com/reference/android/Manifest.permission#USE_EXACT_ALARM.
- `setAndAllowWhileIdle()` es inexacta, NO requiere permiso y dispara en Doze (limitada: ~1 por 15 min por app en Doze según AOSP; la tabla de power-details indica 7/hora para while-idle). Fuentes: https://source.android.com/docs/core/power/platform_mgmt ("During Doze") ; https://developer.android.com/topic/performance/power/power-details.
- Apps exentas de optimización de batería pueden agendar alarmas exactas SIN `SCHEDULE_EXACT_ALARM`: "Apps targeting S or higher can schedule exact alarms only if they have the SCHEDULE_EXACT_ALARM permission or they are on the device's power-save exemption list"; notas de API: "unless the app is exempt from battery restrictions". Fuente: https://developer.android.com/reference/android/app/AlarmManager (canScheduleExactAlarms y notas de setExactAndAllowWhileIdle).
- `setAlarmClock()` permite salir de Doze y el sistema usa la info para mostrar el próximo "alarm clock" a la usuaria (ícono visible en status bar). Fuente: https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo, android.app.PendingIntent) ; análisis secundario: https://proandroiddev.com/beyond-doze-building-reliable-background-execution-on-modern-android-including-oem-realities-5fa0a6e05672.
- Recomendación para tracking (no despertador): NO usar `USE_EXACT_ALARM` ni `setAlarmClock()`; usar FGS + watchdog con `setAndAllowWhileIdle()`/`setWindow()` inexactas, y si se necesita exactitud, aprovechar la exención de batería (que ya se pide por Doze) para alarmas exactas. Fuente: https://developer.android.com/develop/background-work/services/alarms ("Use cases that might not require exact alarms").

## 4. Foreground Service (arranque y requisitos)

- Objetivo correcto: FGS tipo `location` con `ACCESS_BACKGROUND_LOCATION`; cubre tracking continuo y el while-in-use. Fuente: https://developer.android.com/develop/background-work/services/fgs/service-types ("Location").
- target 31+: prohibido iniciar FGS desde background salvo excepciones. Lista oficial: transición desde estado visible; poder iniciar activity desde background; FCM de alta prioridad; interacción de usuaria (notificación/bubble/widget); alarma exacta pedida por la usuaria; IME; transición de geofence/activity recognition; `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`/`MY_PACKAGE_REPLACED`; `SYSTEM_ALERT_WINDOW` (desde 15: con overlay visible). Fuente: https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start ("Exemptions from background start restrictions").
- while-in-use: para crear FGS `location` desde background se exige `ACCESS_BACKGROUND_LOCATION`; con ese permiso el servicio accede a ubicación siempre. Fuente: restrictions-bg-start ("Restrictions on starting foreground services that need while-in-use permissions").
- `BOOT_COMPLETED`: exención válida para FGS; en 14+ hay restricciones por tipo y `location` está exento en 15/16. Requisito: location ON + permiso, si no hay `SecurityException` (issuetracker 294408576). Fuentes: restrictions-bg-start ; https://developer.android.com/about/versions/15/behavior-changes-15 ; issuetracker.
- La exención de optimización de batería NO figura entre las exenciones de background-start de FGS; solo habilita red/wake locks en Doze y alarmas exactas. Fuentes: restrictions-bg-start (lista) ; doze-standby.
- Android 14+: cada tipo tiene su permiso (`FOREGROUND_SERVICE_LOCATION`); declarar bien evita `SecurityException`. Fuente: https://developer.android.com/about/versions/14/changes/fgs-types-required.
- Android 14+: la usuaria puede descartar la notificación del FGS (no así detener el servicio; eso es el Task Manager). Fuente: https://developer.android.com/about/versions/14/behavior-changes-all ("Dismissible foreground notifications").
- No usar `dataSync` para subidas largas (timeout 6 h/24 h en target 35+); `location` no tiene timeout. Fuente: https://developer.android.com/develop/background-work/services/fgs/timeout.

## 5. REQUEST_INSTALL_PACKAGES y OTA sideload

- Android 8 (API 26)+: permiso por app "Install unknown apps"; la app declara `REQUEST_INSTALL_PACKAGES` y la usuaria lo habilita en Ajustes > Apps > Acceso especial; sin él, AOSP aborta la instalación originada por esa app (target ≥26). Fuentes: https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls() ; AOSP https://android.googlesource.com/platform/frameworks/base/+/master/packages/PackageInstaller/src/com/android/packageinstaller/InstallStart.java.
- Chequeo y apertura: `PackageManager.canRequestPackageInstalls()` (26+) y `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` con `package:<app>`; opción `ACTION_VIEW` con FileProvider (`content://`, mime `application/vnd.android.package-archive`, `FLAG_GRANT_READ_URI_PERMISSION`); alternativa `PackageInstaller.Session` con `IntentSender` de estado. Fuentes: PackageManager ref ; https://developer.android.com/reference/android/content/pm/PackageInstaller ; https://developer.android.com/reference/android/provider/Settings ; hilo secundario: https://stackoverflow.com/questions/4967669/android-install-apk-programmatically.
- Actualización: misma firma + mismo package + versionCode mayor. Android 14 "update ownership": un instalador que no es dueño del update puede disparar diálogo a la usuaria; el self-update con el propio instalador no lo activa. Fuente secundaria: https://www.androidpolice.com/android-14-update-ownership-warning-play-services/.
- Android 14 bloquea instalar APKs con target <23 (override por ADB). Irrelevante para target 35, pero documentado. Fuente: https://issuetracker.google.com/issues/271985457.
- Android 13 "restricted settings" (sideload): aplica a Accessibility/Notification Listener y otros ajustes sensibles, NO a la instalación normal; la usuaria debe habilitar "Permitir ajustes restringidos" en App info. Fuente secundaria: https://stackoverflow.com/questions/72217216/android-13-enable-accessibility-service-for-apk-which-installed-not-from-googl.
- Política Play de `REQUEST_INSTALL_PACKAGES` (solo si se publica en Play): la funcionalidad core debe incluir enviar/recibir paquetes y habilitar instalación iniciada por el usuario; el auto-update silencioso fuera de Play está prohibido para apps de Play. Fuentes: https://support.google.com/googleplay/android-developer/answer/12085295 ; https://support.google.com/googleplay/android-developer/answer/16559646.

## 6. Lo que NO se puede hacer (honesto)

- Autostart OEM (MIUI, ColorOS, EMUI, etc.): NO hay API pública para habilitarlo, leerlo ni concederlo; solo abrir pantallas OEM por `ComponentName` (frágil, puede no existir; cambia por versión). Fuentes secundarias: https://stackoverflow.com/questions/38995469 ; https://stackoverflow.com/questions/34149198 ; https://stackoverflow.com/questions/39366231 ; https://github.com/XomaDev/MIUI-autostart.
- Conceder permisos runtime por código: imposible para una app normal. `adb shell pm grant` requiere ADB. `DevicePolicyManager.setPermissionGrantState()` solo para Device/Profile Owner; en Android 12+ el Profile Owner NO puede conceder sensores (incluye `ACCESS_FINE/COARSE/BACKGROUND_LOCATION`); el Device Owner sí, salvo opt-out de provisión. Fuente: https://developer.android.com/reference/android/app/admin/DevicePolicyManager#setPermissionGrantState(android.content.ComponentName,%20java.lang.String,%20java.lang.String,%20int).
- Activar un `AccessibilityService` por código: no; "Starting an accessibility service is triggered exclusively by the user explicitly turning the service on in device settings" (AOSP). Solo se puede abrir `ACTION_ACCESSIBILITY_SETTINGS`; en sideload 13+ la usuaria debe habilitar "Allow restricted settings" primero. Fuentes: AOSP https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/accessibilityservice/AccessibilityService.java ; https://developer.android.com/reference/android/provider/Settings#ACTION_ACCESSIBILITY_SETTINGS ; SO 72217216.
- Setear AppOps (`appops set ...`) desde la app: no; el estado de app-ops lo cambia el sistema/ADB. APIs ocultas/non-SDK restringidas → `SecurityException`. Fuentes: AOSP AppOps https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android13-security-release/core/java/android/app/AppOps.md ; https://developer.android.com/about/versions/13/changes/non-sdk-13.
- Añadirse a la allowlist de Doze sin interacción: no; solo diálogo del sistema o Ajustes. Fuente: doze-standby.
- Matar/arrancar/forzar otras apps: `killBackgroundProcesses()` solo afecta a la propia app desde Android 14; no hay API para iniciar otras apps en background. Fuente: https://developer.android.com/about/versions/14/behavior-changes-all.
- Abrir Ajustes o pantallas OEM desde background: bloqueado por BAL salvo excepción (notificación con tap, ventana visible, SAW). Desde Android 14, al enviar un `PendingIntent` el emisor debe hacer opt-in (`setPendingIntentBackgroundActivityStartMode`) para transferir privilegios BAL. Fuente: https://developer.android.com/guide/components/activities/secure-bal.
- Leer `PACKAGE_USAGE_STATS`/standby bucket de otras apps sin grant: no; es acceso especial y `getAppStandbyBucket(String)` es SystemApi. Fuentes: UsageStatsManager ref + AOSP.

## 8. Checklist operativo para el equipo (derivado, no normativo)

- Pedir: `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION` juntos → luego `ACCESS_BACKGROUND_LOCATION` con UI educativa + deep link a Ajustes de la app; nunca juntos.
- Pedir `POST_NOTIFICATIONS` antes de arrancar el FGS (canal propio de tracking).
- Manifest: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, `POST_NOTIFICATIONS`, `ACCESS_BACKGROUND_LOCATION`, `RECEIVE_BOOT_COMPLETED`, `REQUEST_INSTALL_PACKAGES`.
- Arranque en boot: verificar location ON y permisos; si `startForeground()` lanza `SecurityException`, registrar y reintentar (no crashear).
- "Sobrevivir": FGS `location` + exención de optimización de batería (diálogo) + watchdog con alarmas inexactas; NO usar `dataSync` ni `USE_EXACT_ALARM`/`setAlarmClock`.
- OTA: descargar APK, `canRequestPackageInstalls()` → si false abrir `ACTION_MANAGE_UNKNOWN_APP_SOURCES`; instalar con `ACTION_VIEW` + FileProvider (o `PackageInstaller.Session`).
- Diagnóstico: `isIgnoringBatteryOptimizations`, `isBackgroundRestricted`, `getAppStandbyBucket()` (propia app), y guía manual a Ajustes OEM por fabricante (sin API).
